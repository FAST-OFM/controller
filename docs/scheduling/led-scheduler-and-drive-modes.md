# LED Scheduler and Drive Modes

## Principle

Firmware schedules logical LED patterns. It must not assume the physical LED driver type.

Logical patterns:

```text
BF_WHITE
AF_RED_GREEN
DARK
CUSTOM
```

Physical drive modes:

```text
controller_mosfet_resistor
board_mosfet_resistor
external_constant_current
external_fast_strobe
```

The same scan recipe should remain valid after the physical LED hardware is upgraded, as long as the illumination profile declares compatible timing capabilities.

## Revision A behavior

Revision A may use small LEDs powered from a verified controller-board low-voltage rail and switched by MOSFETs or board outputs.

Firmware requirements:

- LED pins default OFF at boot.
- LED pins go OFF on fault, abort, pause, and safe shutdown.
- LED patterns are generated by the timing MCU, not Linux userspace.
- LED pattern identity is included in every `FRAME_EVENT`.
- Pulse width, trigger lead/tail timing and brightness are configurable per
  pattern through `pattern_led_timing`.
- Slow scan modes are allowed if LEDs require long exposure.

## Pattern Timing Profiles

Scan recipes use `pattern_led_timing`, keyed by logical pattern name. The
profile is selected for each position-indexed frame before timing metadata is
emitted. Every pattern named by a scheduled stripe must have a reviewed
profile. The scheduler emits the selected profile into the per-frame
`led_timing` metadata contract while keeping `hardware_outputs_enabled=false`.

```yaml
pattern_led_timing:
  BF_WHITE:
    frame_period_us: 2500
    exposure_start_offset_us: 100
    exposure_us: 1000
    gate_pulse_us: 200
    trigger_pulse_us: 80
    brightness_by_gate:
      led_white: 0.7
  AF_RED_GREEN:
    frame_period_us: 2000
    exposure_start_offset_us: 200
    exposure_us: 600
    gate_pulse_us: 0
    trigger_pulse_us: 200
    gate_pre_trigger_us: 150
    gate_post_exposure_us: 75
    baseline_gate_names: [led_white]
    brightness_by_gate:
      led_red: 0.8
      led_green: 0.3
```

`BF_WHITE` normally drives only `led_white`. `AF_RED_GREEN` may drive
`led_red` and `led_green` together under one envelope while suppressing the
white preview baseline before trigger and restoring it after exposure. The
old flat recipe field `led_timing` is rejected.

## Future driver behavior

Future external drivers may have enable pins, PWM pins, current-set DACs, current monitors, and thermal monitors.

Firmware must expose driver-specific functionality through configuration, not through separate scan logic.

## Current Feedback Rule

Brightness setpoints and timing gates are separate concerns in Rev A:

- Arduino Nano PWM outputs may provide filtered VREF/current-setpoint signals.
- The timing MCU still owns frame-synchronous LED gate pulses.
- Sense-resistor ADC feedback is valid only while the matching LED current path
  is enabled.
- Calibration maps scanner brightness `0..255` onto a reviewed raw PWM/VREF
  range for each LED channel.
- Normal runtime should use calibrated brightness values, not raw PWM values.
- Runtime pulsed operation must use calibrated setpoints, gate-synchronized
  on-window sampling, or a reviewed analog peak/hold/current-monitor circuit.
- Do not interpret ADC readings taken during LED off-time as LED current.
- Do not implement a scan-time current loop through USB serial commands.

## LED Calibration Workflow Model

The software calibration model has two explicit modes:

- Calibration mode consumes already-measured sense-resistor samples and builds
  a normalized brightness/current lookup for one logical LED channel.
- Runtime mode consumes an existing lookup and resolves validated target
  currents to calibrated brightness setpoints.

Calibration records must include the logical channel, requested brightness,
measured sense-resistor voltage and whether the matching LED current path was
on during the sample window. Samples captured while the LED path is off are
invalid and must not be folded into the current lookup.

Each calibrated channel must carry sense-resistor metadata: resistance in ohms,
power rating in watts and reviewed target-current limits. The model converts
recorded millivolts across the resistor to milliamps, checks the resistor power
rating and rejects target currents outside the channel limits or calibrated
current range.

The model is software-only. It must not perform live ADC reads, toggle LED
gates, change PWM/VREF outputs or poll hardware during scan runtime.

## Guardrails

- Do not toggle real LED outputs during board discovery.
- Use simulator or dry-run events first.
- Unknown pins remain unknown until board discovery documents them.
- Do not enable fly-scan pulse widths shorter than the measured driver capability.
- Do not assume LED pulse occurs inside exposure until verified with oscilloscope.

## MKS V1 Atomic Illumination Window

Backlog item `199 [P0]` tracks the low-level scanner-firmware contract for the
current no-motion autofocus illumination window. The timing MCU owns the full
window; the Raspberry Pi must not issue separate Linux-timed `SET_PIN` commands
for frame-synchronous red/green illumination.

The V1 sequence is:

```text
white off -> red+green on together -> settle -> XVS trigger
-> exposure hold -> red+green off together -> white restore
```

The software contract is implemented as disabled-output metadata. It attaches
logical timing to `FRAME_EVENT`, uses MCU time as the trigger reference and keeps
`hardware_outputs_enabled=false`. It may name the current MKS pin mapping as
context (`PD6` trigger, `PA9` green, `PA10` red, `PB13` white, active high), but
the code path must remain logical-alias only until a separate reviewed
bench-safe issue approves live outputs.

The scan trigger is position-indexed. `frame_start_us` is the MCU timestamp of
the position event, not the scheduling authority. Step/position reach starts the
AF window, then MCU-local timers apply the configured settle, XVS pulse,
exposure hold and restore offsets.
